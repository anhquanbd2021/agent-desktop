Two ways to see the same screen

What the lab models

Computer-use agents perceive a desktop in one of two ways:

  • Pixels. Take a screenshot, feed it to a vision model, get back text and approximate coordinates. The model pays for the whole image every step and still has to guess what each element is.
  • Structure. Ask the OS for the accessibility tree — the same API screen readers have used for decades (macOS Accessibility API, Windows UI Automation, Linux AT-SPI). Every element arrives with a role, name, state, and supported actions.

The lab renders one fixture scene both ways so the trade-offs are visible side by side. It is inspired by agent-desktop, a Rust CLI that exposes real desktop accessibility trees to agents with deterministic @eN refs and JSON output.

Reading the token budgets

Three counters, one scene:

  • Screenshot — image tokens scale with resolution, not with content: an empty desktop and a dense Slack window cost the same. Our model uses ≈ pixels/750 plus a text-reading surcharge.
  • Full tree — scales with node count. Small windows are cheap; dense apps can exceed a screenshot. The real tool measured a full Slack snapshot at 30,743 tokens.
  • Skeleton — a shallow overview: only top-level containers, each annotated with children_count. The real tool's Slack example drops to 383 tokens — a 78–96% reduction on dense apps. The agent then drills into one ref (--root @e3) and pays only for that region.

The query deck

Six questions score each mode answered / guesses / blind:

Click "Send"answeredguessesTree returns a ref + press action; pixels return coordinates that shift with layout.

Window titleansweredansweredThe one thing OCR reads reliably.

The point is not "tree always wins" — it is route perception per question. Structure for controls and state; pixels for genuinely visual questions; a hybrid agent uses both.

Honest limits

  • Token counts are a documented chars/4 estimate plus a pixels/750 image heuristic — a comparison tool, not a tokenizer benchmark.
  • The raster is a schematic, not a real screenshot; real vision models fail in more interesting ways (occlusion, styling, adversarial UI).
  • Fixture trees are well-formed; real apps ship missing names, wrong roles, and custom widgets that expose nothing at all.
  • Answerability ratings are illustrative, not a benchmark of any specific vision model.
